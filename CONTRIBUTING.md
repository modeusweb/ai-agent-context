# Contributing

Thanks for taking the time. This document covers the workflow that keeps the
three published packages in sync and the review expectations that apply to
analysis changes.

## Setup

```bash
npm install
npm run verify
```

`npm run verify` is the gate: it builds all packages, typechecks the test tree
and runs the full suite. Run it before every push.

### Which Node version

Two different floors, for two different reasons:

| | Floor | Why |
| --- | --- | --- |
| **Published packages** (`ai-agent-context`, `@ai-agent-context/*`) | `>= 20.11.0` | They ship compiled JavaScript with no runtime dependencies. Nothing in the code needs a newer Node. |
| **Working on this repository** (build, `npm run verify`) | `>= 22.18.0` | The test suite is TypeScript and runs through Node's native type stripping, which is unflagged from 22.18. On Node 20 the build succeeds and the tests cannot start at all. |

CI mirrors this: the `test` job runs the TypeScript suite on Node 22.18 and 24
across Linux, Windows and macOS, while `npm run smoke` packs the real tarballs
and exercises them on Node 20.11 as well. If you bump `engines.node`, the smoke
job is what will notice.

```bash
npm run smoke     # pack, install into a clean project, drive the CLI and MCP
```

`npm run smoke` is deliberately not a unit test: it is the only thing that
validates the published artifacts, and it runs on a repository built to contain
the inputs that have broken things before — an import that climbs two
directories, and an import that tries to escape the repository root.

## Repository layout

```
packages/core   # @ai-agent-context/core — analysis engine, zero runtime deps
packages/cli    # ai-agent-context — the `agent-context` CLI
packages/mcp    # @ai-agent-context/mcp — MCP stdio server
fixtures/       # synthetic repositories used by tests and the benchmark
tools/          # repo automation (fixtures, benchmark, versioning, clean)
```

Only `packages/core` may be depended on by the other two. Core keeps **zero
runtime dependencies** on purpose — it is what makes the tool installable
anywhere and safe to run on untrusted repositories. Adding a dependency to core
needs a strong justification and a note in `MIGRATION.md`.

## Working on analysis code

Analysis output is a **contract**, not a debug dump. Every value that is not
read directly out of the repository must carry a `confidence` and `evidence`.

- Heuristics must be deterministic. No `Date.now()`, no randomness, no
  iteration over unordered collections without sorting it first. The
  `determinism` test enforces this — if your change makes two scans of the same
  commit differ, that is a bug, not a tolerance question.
- Never assert a fact the tool cannot prove. "This module depends on payments"
  is an observation; "this module is the domain layer" is a heuristic and needs
  confidence plus evidence.
- If you change what a heuristic outputs, update `MIGRATION.md`. Users persist
  `.agent/` in Git and diff it across releases.

## Adding tests

Tests run with the built-in Node test runner (`node --test`). Fixture
repositories are generated by `npm run fixtures` and are copied into a temp
directory per test — never mutate a committed fixture in place.

**Never pass a path under `fixtures/` to `AgentContext.load()`.** Scanning writes
`.agent/` into the directory it scans, which would pollute the committed
fixtures with generated context and a local parse cache. Always go through
`createTempRepo()` from `packages/core/test/helpers.ts`:

```ts
import { cleanupTemp, createTempRepo } from './helpers.ts';

const root = createTempRepo('layered-app');
tempRoots.push(root);
const context = await AgentContext.load({ root });   // temp copy, not fixtures/
```

New analysis behaviour needs a test that would have failed before the change.
That specifically means covering:

- the awkward inputs (relative imports that climb directories, `..` traversal
  attempts, re-exports, barrels, dynamic imports);
- the bound, not only the happy path;
- an assertion on the *outcome* (does this dependency edge exist?), not only on
  the shape of the payload.

## Versioning and releases

All three packages share one version, held in
`packages/core/src/model/version.ts`. Do not edit it by hand:

```bash
node tools/set-version.mjs 0.6.0
npm run verify
npm run smoke
git commit -am "chore(release): v0.6.0"
npm run publish:all
```

`publish:all` publishes core first — cli and mcp depend on it, so publishing in
the other order would stage a release that cannot resolve its own core.

Set `NPM_TOKEN` in the environment before publishing; the token is read from
there and never written to a file.

Before a release, work through the release checklist at the end of
[ROADMAP.md](ROADMAP.md).

## Pull requests

- One concern per PR. A refactor and a behaviour change in the same diff cannot
  be reviewed.
- Update `README.md` when you add or change a CLI command, MCP tool or config
  key; update `ROADMAP.md` when you finish or change a planned milestone.
- If you touch anything security-relevant (path handling, symlinks, secret
  filtering, MCP transport), say so explicitly in the description and add a
  test that exercises the failure, not just the success.

## Reporting bugs

Open an issue with the command you ran, the repository layout that reproduces
it (a small synthetic repo is ideal) and what you expected instead. Please do
not paste real credentials or private source into an issue.
